# Elliott BTC v2 개선 및 검증 결과

검증일: 2026-10-03. Python 3.13.3 / macOS arm64.

## 결론

후보 선택 범위, 비용 제한, 위험 통제, 감사 기록과 GUI를 개선했습니다. **수익률 상승 또는 실제 최대 낙폭 감소는 입증하지 못했습니다.** 실계좌에 새 전략을 자동 적용하지 않았고, 개발 검증에서 실계좌 주문·입출금은 0건입니다.

## 구현

- 기존 strict 전략과 선택형 `ew-multiscenario-2.0`을 분리했습니다. 기존 저장 설정의 전략은 strict로 유지됩니다.
- 4시간·1시간의 추진 3파/5파, 상위 추진 완료 위치가 확인된 지그재그 C파를 비교합니다. 30분봉은 1시간봉 내부 구조와 새 돌파의 확인에 사용합니다.
- 후보별 구조·상위 맥락·최근성·비용 후 손익비·반대 후보 충돌을 검사합니다. 순위는 고정 규칙 점수이며 승률은 미산정입니다.
- 불명확한 맥락은 위험 배수 0.5, 확인된 정합 1시간 후보는 0.75를 적용합니다. 기본 거래당 위험 자체를 늘리거나 레버리지를 올리지 않았습니다.
- 일일 진입 한도, 청산 후 대기, 연속 손실 휴식, 관측 자산 고점 대비 손실 제한, 남은 손실 예산 내 수량 산출을 실운용과 재생에 공통 적용했습니다.
- 관측 파동 방향과 이후 예상 방향, 후보 비교와 탈락 근거, 계획 위험 배수, 기존/신규/비용 스트레스 비교를 화면과 거래 MD에 반영했습니다.

## 기존 엔진 설정 화면 호환 수정

새 화면이 구버전 서버의 `strategy_mode` 부재를 이유로 기존 배정 자본 입력까지 잠그는 회귀를 수정했습니다. 이제 서버가 반환한 기존 설정만 편집·전송하고, 미지원 신규 필드는 숨깁니다. 새 엔진으로 재시작하지 않아도 기존 서버의 배정 자본을 수정할 수 있습니다. 저장 후 계정 검사는 별도로 다시 수행하며, 과거의 담보 미통과를 근거 없이 통과로 표시하지 않습니다.

`scripts/verify_elliott_settings_compat.py`는 모든 HTTP를 가로챈 모의 화면에서 구버전 13개/신버전 21개 필드의 저장과 재조회, 체크박스 false, 미지원 필드 제외, 이전 검사 결과 폐기를 확인합니다. 두 경우 모두 739에서 736으로 모의 저장 성공, 실제 네트워크 요청 0건입니다. 실행 중인 LIVE 화면에서는 비-GET 요청을 전부 차단한 상태로 배정 입력·저장 버튼 활성만 확인했습니다. 이 점검은 실제 배정 금액이나 매매 상태를 바꾸지 않습니다.

## 1~10배 지원 확대

사용자 요청에 따라 설정·수량 계산·거래소 설정 요청·주문 직전 검증을 공통 1~10배 정수 범위로 변경했습니다. 기본 배율은 1배로 유지합니다. API 상태에 지원 범위를 명시하며 GUI는 실행 중인 서버의 실제 지원 범위를 사용합니다. 초기 화면에서 저장된 10배가 HTML 기본 상한 5배 때문에 잘못 표시되지 않는지도 검사했습니다.

- 전체 **164개 단위·회귀·HTTP 테스트 통과**, 건너뜀 없음. 10배 저장과 11배/소수/비정상 입력 거절, 10배 거래소 설정 요청 형식, 진입 전 보호 검사 유지 등을 모의 응답으로 확인했습니다.
- 현재 자본 736/위험 0.5%/명목 상한 900 조건에서 5배와 10배의 수량·위험 예산·손절·목표·손익비가 같은지 롱/숏 모두 검사했습니다. 단순 추정 초기 증거금은 절반입니다. 명목 상한을 높여 증거금 제한이 지배하는 다른 조건에서는 수량이 증가할 수 있지만 계획 위험 예산을 초과하지 않는지 별도로 검사했습니다.
- 완전히 가로챈 모의 브라우저에서 구버전 상한 5배 유지, 신버전 10배 저장·새로고침 후 10배 유지 검사를 통과했습니다. 실제 네트워크 요청 0건입니다.
- 중단·무포지션·미결 주문 없음 확인과 SQLite 백업 후 8765 LIVE 및 63255 PAPER 서버를 새 코드로 갱신했습니다. 기존 저장 설정과 자산 잔액이 유지됨을 확인했습니다. LIVE는 자본 736 USDT, **현재 5배**, strict 전략, 신규 진입 중단입니다. PAPER는 현재 1배, multi 전략, 신규 진입 중단입니다.

이 시점부터 앞 절의 'LIVE는 이전 코드' 상태는 더 이상 해당하지 않습니다. 새 위험 통제도 로딩되었지만 전략을 multi로 바꾸거나 실제 계정의 레버리지를 변경하지 않았고 매매를 시작하지 않았습니다. 지원 확대 검증은 10배 실체결 또는 수익성 검증이 아닙니다. 실제 청산 가격의 완전한 모델링은 여전히 미지원입니다.

## 후보별 차트 해설

2026-10-03, 정적 화면에 `차트 읽기 · 현재 후보 해설`을 추가했습니다. 매매 엔진·설정·파동 규칙은 변경하지 않았으며 서버를 재시작하지 않았습니다. 페이지를 새로고침하면 적용됩니다.

- 표시 시간봉과 후보에 맞춰 피벗 가격, 어떤 가정이 깨지는지, 무효화와 더 가까운 손절의 차이, 목표 산식을 풀어서 설명합니다. 3파·5파·C파·ABC 완료 가설·추진파 완료 가설·관망 대안을 구분합니다.
- 롱/숏의 유효 손절 거리와 최소 비용 후 손익비로 참고 하한/상한을 계산합니다. 후보 손절·목표를 거래소 호가 단위에 맞추고 진입 경계는 허용 방향 안쪽으로 표시합니다. 이는 주문 가능 범위가 아니며 설정 수수료를 사용한 예시입니다. 실제 계정 수수료가 더 높거나 비용 비중·추격·신호 만료·수량·위험 조건을 충족하지 않으면 주문할 수 없습니다.
- 후보에 연결된 종가 돌파 기준만 표시하고 다른 후보의 신호를 섞지 않습니다. 돌파 종가 조건을 시장가 진입 호가의 직접 하한/상한으로 오인하지 않도록 설명합니다. 연결된 신호가 없으면 실제 돌파 경계를 미확정으로 표시합니다.
- 가정 진입가 입력은 브라우저 내 계산만 수행합니다. 기본은 롱 ask / 숏 bid이며 호가가 없으면 최근 종가나 MARK_PRICE로 대신하지 않습니다. 출력은 1 BTC당 손실·목표 순손익·손익비이며 실제 수량 적용과 수동 주문 보호의 한계를 명시합니다.
- `scripts/verify_elliott_guide_ui.py`: 네트워크 전체 모의 응답, **108개 롱/숏·수수료·슬리피지·손익비·호가 단위 조합**을 Python `execution.payoff`와 대조했습니다. 경계에서 통과하고 불리한 방향으로 한 틱 넘어가면 미달인지 확인했습니다. 후보 변경 시 입력 초기화, 같은 후보 갱신 시 입력 유지, 숏 방향, 불가능한 범위, 후보 없음, 호가 없음, 지연과 만료도 검사했습니다.
- 1440/390/360px의 모의 브라우저와 실제 8765 LIVE / 63255 PAPER 화면을 확인했습니다. 글자·페이지 넘침, JS 오류 없음, 차트 캔버스 픽셀 확인. 실제 화면 점검에서는 모든 비-GET/외부 요청을 차단했으며 설정·가동 여부·포지션·미결 상태 불변을 확인했습니다. 거래 요청 0건입니다.
- 전체 **164개 단위·회귀·HTTP 테스트 통과**, 건너뜀 없음. 스크린샷은 `artifacts/elliott-guide-ui/`에 보관합니다. 이 검증은 화면·계산 일치 검증이지 투자 성과나 파동 해석 정확도의 인증이 아닙니다.

## 수동 진입가의 손절·익절 비교 확장

`static/manual.js`에 주문과 분리된 수동 참고 계산을 추가했습니다. 입력 진입가, 진입 전/이미 체결 구분, 후보와의 방향 일치, 선택 BTC 수량으로 파동 끝점 손절과 피보나치 목표별 순손익·손익비를 비교합니다. 목표 산식은 규칙집 19절의 고정 정책입니다. 자동 엔진의 목표·손절·레버리지·설정에는 변경이 없습니다.

- 기본 목표를 2.618배 등 먼 목표로 자동 교체하지 않는지, 진입가를 바꿔도 구조 가격은 동일한지 검사했습니다. 5파의 L3 길이 제한을 롱/숏에 대칭 적용합니다.
